## OPP-15 — DUAL-ARM cellの表現

1. 裁定（推奨）: 第3案「B+」。現行のarm別`ArmSpec`を維持し、`CellKinematicLayoutRef`相当のcontent-addressed参照を追加します。そこに左右armのbase transform、robot instanceとの対応、共有collision modelを束縛します。案Aは目標cellをschema 1.0の適用外にするため採りません。
2. 根拠: RS71のDUAL-ARMは「cellにarmが2本ある」ではなく、「every motionで両腕が保持・操作する」という実行上の不変条件です。一方、現行`ArmSpec`はarm別serial、firmware、controller envelope、tool/TCPを正しく分離していますが、`WorkspaceRestriction`は単一TCPの点／線分を評価する単項制約で、固定base配置とarm間の相対状態をまだ表現しません。
3. 条件: `P_ARM_COVERAGE`に加えて、①schema 1.0では`ee_left`・`ee_right`・`gripper_left`・`gripper_right`のcell capabilityを必須化、②左右EEと左右gripperの対応を一意化、③arm別base transformをhash束縛、④profileに静的なarm間keep-out／minimum-separation／swept-volume predicateをcontent hash付きで保持、⑤CommandGatewayは両armの提案状態を同一snapshotで連言評価、⑥ISLは実測状態で動的干渉を独立監視、⑦commissioningで左右入替・片腕欠落・base transform改変・相互衝突のnegative controlを要求します。profileの検査は両腕能力の存在までとし、「every motionで両腕が活動する」という合成・実行適合性は別のruntime／composition検査に残します。
4. 不変前提への影響: なし。 B+はDUAL-ARMを単腕化せず、88 mm span／固定baseを変更せずに参照・測定可能にするだけです。DiffIK-only、gripper geometry LOCK、no-kinematic-trickにも変更を加えません。ただし、案Bの採用だけを理由に「DUAL-ARM充足済み」と宣言するのは不可です。
5. 実装への含意: 凍結`contracts_v2`／EvidencePolicy／`TensorBindingSpec`へのschema deltaは0を維持できます。動くのはdeployment profile候補のみで、`ArmSpec.base_transform_ref`を加えるか、cell-levelの`CellKinematicLayoutRef{artifact_sha256}`を追加します。arm間静的制約は既存の単項`WorkspaceRestriction`へ曖昧に混入させず、`InterArmRestrictionSet`または外部collision-model参照として分離するのが妥当です。`robot_model_ref`はschema 1.0では全arm共通のUR15制約を維持し、各armが実際にそのmodelであることをarm別commissioning evidenceで確認します。異機種混在を将来許す場合だけarm別`robot_model_ref`へschema bumpします。

## OPP-11 — RuntimeTimeoutsの絶対上限と順序制約

1. 裁定（推奨）: 第3案。 数値上限を05／06本文に直接固定せず、RT0またはcell safety courtが発行するcontent-addressedな`CellSafetyTimingBaseline`を唯一のceiling sourceとします。profile acceptance recordが`profile_hash`と`timing_baseline_hash`を同時に束縛し、各`RuntimeTimeouts`値について`value ≤ approved_ceiling[field]`を`P_TIMEOUT_CEILING`で検査します。
2. 根拠: これら13 fieldに共通して適用できる普遍的な秒数は、robot model、controller、network、gateway、stop性能、hazard geometryを無視して決められません。ISO 12100は機械ごとのrisk assessment／risk reductionを基礎とし、ISO 10218-2:2025はrobot cellのintegration・commissioning・operationをintegrator側の対象にします。ISO 13849-1:2023も方法論を定めますが、個別applicationの安全機能や必要性能を一律には指定しません。IEC 62061は安全関連制御系の設計・統合・validationを扱い、ISO 13855:2024は応答時間を含む保護距離算定の枠組みを与えます。
3. 条件: ①`ack_timeout_s ≤ boundary_dwell_s`は採用しますが、さらに`max_reselect_attempts × 1試行の最悪時間 + selector overhead ≤ boundary_dwell_s`を要求、②`health_confirm_timeout_s < lease_max_duration_s`を採用し、同時満了を避ける、③現行`decision_max_age_s ≤ permit_ttl_s`は撤回し、`permit_effective_expiry = min(issued_at+permit_ttl, ack.valid_until, decision_time+decision_max_age, profile-acceptance expiry, calibration/evidence expiry)`としCASで再検査、④`safety_heartbeat_timeout + detection + gateway切替 + measured stop time ≤ safety response budget`等のend-to-end上限をbaselineに持たせます。commissioning evidenceにはfault codeの発火だけでなく、worst-case負荷下の検出からSafeHold／SafeStop到達までの実測上限、clock異常、scheduler stall、通信喪失を含めます。
4. 不変前提への影響: なし。 timeout ceilingはcell runtimeのfail-closed性能を制限するもので、DUAL-ARM、88 mm span／固定base、DiffIK-only、gripper geometry、no-kinematic-trickの意味を変更しません。
5. 実装への含意: 凍結schema deltaは0を維持できます。06には必ずしも新fieldを足さず、OPP-13の`ProfileAcceptanceRecord`へ`timing_baseline_hash`を持たせる構成が最も循環しにくいです。05側では`CommitPermit.effective_expires_at`または同値の導出規則、CAS時のdecision age／acceptance／evidence有効性再検査、06側では`P_TIMEOUT_CEILING`と集約順序検査を追加します。

## OPP-13 — profile registryの所在・受理・失効権限

1. 裁定（推奨）: 第3案。 `accepted_profiles`／`revoked_profiles`の裸の集合ではなく、append-onlyの`ProfileRegistry`と不変な`ProfileAcceptanceRecord`を導入します。状態は少なくとも`PROPOSED | ACCEPTED | SUSPENDED | REVOKED`とし、`REVOKED`は終端、再使用は新acceptance generationのみとします。
2. 根拠: 現行文書はpermit発行時に受理済み・未失効を要求し、AuthorityState自体もdurableで復元不能時は起動拒否としていますが、profile受理の根拠・許可mode・validator/evidence/timing baseline・承認者を固定していません。またpermit後にrevocationされても、現在のCAS条件はprofile registryを再検査しません。
3. 条件: 受理は①全`P_* = 0`を必要条件、②SHADOW専用acceptanceはcell commissioning担当＋独立reviewer、③CLOSED_LOOPを許可するacceptanceは「独立safety approver」と「deployment／operations custody approver」のtwo-key、④cell operator単独ではclosed-loop不可、とします。失効は非対称にし、incident、ISL異常、layout/tool/controller/safety-layer identity変更のいずれでも、認可された一者または自動monitorが即時`SUSPENDED`にできます。解除・再受理は原因除去evidence＋新generation＋two-keyを必要とし、旧revocationを削除しません。recordは`profile_hash`、allowed lease modes、validator/policy hash、deployment-evidence-set hash、timing-baseline hash、cell/layout identity、承認role、期限を固定します。
4. 不変前提への影響: なし。 これはdeployment profileを誰がどの根拠で有効化できるかというgovernance／authority境界であり、RS71のロボット動作前提を変更しません。むしろ不変前提に反するprofileを単独operatorが受理する経路を閉じます。
5. 実装への含意: 凍結schema deltaは0を維持できます。registryはAuthorityManagerと論理的に分離し、同一transactional databaseを使う場合もnamespace、ACL、journal writerを分けます。AuthorityManagerはread-only consumerとし、permitには`acceptance_record_hash/generation`を束縛、CASでなお`ACCEPTED・未失効・未revoked`を再検査します。revocationはpending permitをVOIDにし、active closed-loop leaseをSafeHold／安全理由ならSafeStopへ移します。registryを復元できない場合は、processを診断用SAFEHOLDで起動してもよいものの、permit発行・CAS・actuationは全面拒否とします。

## OP-19 — 活性lease中のcalibration／evidence失効

1. 裁定（推奨）: 第3案。 CLOSED_LOOPでは「次permitまで検出しない」を採りません。ただし一律の短周期pollingでもなく、既知期限に対する決定論的deadline＋変更eventによる即時invalidity通知＋必要な診断だけ周期評価の三層にします。SHADOWはactuationがないため、次permit評価を許容できます。
2. 根拠: 現行既定は曝露を「最大1 skillかつ`lease_max_duration_s`」としていますが、1 skillでもhazardは発生し得て、`lease_max_duration_s`自身も外部ceilingなしでは安全上の上限になりません。現在の文書はcalibration/evidence失効をactive lease中には検出せず、次permitでのみ拒否します。 機能安全系の周期試験・configuration management・validationは安全機能ごとの設計根拠に従うべきで、任意の一律周期からは導けません。
3. 条件: permit／CAS時にwall-clock期限をmanagerのmonotonic clockへ変換し、`lease_valid_until_mono = min(calibration期限, evidence期限, acceptance期限, lease_max_duration)`をleaseへ束縛します。期限到達で`TRANSFER_TO_SAFEHOLD`、安全機能・TCP・停止性能に関わる失効なら`SAFE_STOP`へ強化します。incident、tool交換、firmware更新、layout revision、ISL build変更、record revocationは`DeploymentValidityMonitor`からevent-drivenで通知し、AuthorityManagerが唯一writerとしてCASします。周期再評価が必要なdrift／proof-test項目だけ、RT0 safety caseが定める診断周期とworst-case detection timeを`timing_baseline_hash`に収容します。
4. 不変前提への影響: なし。 活性leaseの有効条件を厳格化するだけであり、RS71の5不変前提を変更しません。失効時の自動継続を禁止するため、fail-closed方向の追加制約です。
5. 実装への含意: 凍結schema deltaは0を維持できます。05のruntime候補には`ActiveAuthorityLease.validity_deadline_mono`、`acceptance_record_hash`、期限導出ref、runtime-only faultとして`R_PROFILE_SUSPENDED`／`R_CALIBRATION_EXPIRED_ACTIVE`／`R_EVIDENCE_EXPIRED_ACTIVE`相当を追加します。これらを`ProducerOutcome`へ追加してはいけません。06は既存`valid_until_iso8601`を再利用でき、周期診断を採る場合だけ外部`DeploymentValidityPolicy`またはRT0 baselineのhash参照を追加します。
