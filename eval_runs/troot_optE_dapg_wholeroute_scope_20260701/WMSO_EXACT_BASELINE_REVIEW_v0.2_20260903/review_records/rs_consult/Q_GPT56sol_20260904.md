## 1. 【最優先】OPP-15 — DUAL-ARM cell を profile でどう表現するか（不変前提に接する）

**背景の事実**
- RS71 §0 不変前提 #1 = **DUAL-ARM**: 「the cable is held + manipulated by BOTH arms (UR15 × 2) in EVERY motion; neither arm is dropped/parked to make it single-arm」（`thread-vault/04-Specs/RS71-System-Spec-SSOT.md:23`）。
- frozen `ControlResourceSpec` は `{ee_left, ee_right, gripper_left, gripper_right: bool}` を資源の語彙として持つ（contracts_v2 DESIGN `:142`）。
- v0.2.3 までの 06 は `CellIdentity` に `robot_serial_ref` / `controller_firmware_ref` を 1 組、`ControllerEnvelope` と `ToolPayloadSpec` を 1 つずつしか持たず、**両腕 cell を宣言できるのに片腕分しか identity / envelope / tool / TCP を検査できなかった**（reviewer R2-04・verifier 確認 HIGH）。

**選択肢**
- 案 A（暫定・schema 1.0 を単一 robot 限定）: `P_MULTI_ROBOT_UNSUPPORTED`（`ee_left` / `ee_right` のどちらか一方のみ True）を足し、dual-arm profile は open に送る。
  - 利点: 型変更が最小。欠点: **目標 cell（UR15 × 2）に schema 1.0 が使えない**。DUAL-ARM 不変前提と衝突する（片腕運用を前提にした profile しか作れない）。
- 案 B（CC が v0.2.4 で暫定採用）: arm 単位の型 `ArmSpec` を導入。
  ```
  class CellIdentity:  cell_id / site_id / robot_model_ref（全 arm 共通・UR15）/ base_frame_ref /
                       arms: tuple[ArmSpec, ...] / safety_layer_ref / layout_revision_ref
  class ArmSpec:       resource_id ∈ {"ee_left","ee_right"}（frozen key・arms 内で一意）/ robot_serial_ref /
                       controller_firmware_ref / controller: ControllerEnvelope / tool_payload: ToolPayloadSpec（TCP は tcp_offset_ref）
  検査 P_ARM_COVERAGE: resource_availability.control で True の ee_left / ee_right ごとに arms に一致 entry がちょうど 1 つ
  CONTROLLER_IDENTITY / TOOL_IDENTITY / ENVELOPE_READBACK / P_ENVELOPE_SHAPE は arm ごとに評価
  05 §4.3 CONTROLLER 項 = command が指す arm の envelope
  ```
  - 利点: 両腕 cell を表現でき、不変前提を変えない。欠点: deployment 層の型が増える（frozen schema delta は 0）。**arm 間の共有 workspace・相互干渉 zone の扱いは未定義**。

**CC の立場（裁定ではない）**: 案 A は不変前提と衝突するため採らず、案 B で本文を書いた。ただし不変前提に接する判断なので Rs の確認を要すると verifier が指摘。

**求める判断**
1. 案 B の採用可否（または第 3 案）。
2. 案 B が RS71 §0 の不変前提（DUAL-ARM / 88 mm grasp span / DiffIK-only / gripper geometry LOCK / no-kinematic-trick）の**いずれにも触れない**ことの確認（触れるなら、どれに、どう）。
3. arm 間の干渉（両腕共有の workspace zone・相互 keep-out）を profile の `WorkspaceRestriction` に持たせるか、ISL の監視に委ねるか。
4. `robot_model_ref` を全 arm 共通（UR15 固定）とする現状で良いか、arm ごとに持たせるか。

## 2. OPP-11 — RuntimeTimeouts の絶対上限と追加の順序制約

**背景の事実**
- profile が timeout 値を供給する（`RuntimeTimeouts` 13 field → 05 `TimingBinding`）。reviewer が「timeout を巨大にすれば安全機構（ISL heartbeat 喪失時 SafeStop・deadline miss・permit 失効）を無効化できる」と指摘（CD-01 HIGH）。
- v0.2.3/v0.2.4 で**相対順序**検査 `P_TIMEOUT_ORDER` を導入済み: `safety_heartbeat_timeout_s ≤ command_deadline_s`；`inter_command_jitter_s < 1/action_rate_hz`；`decision_max_age_s ≤ permit_ttl_s ≤ boundary_dwell_s`；`ack_validity_s ≤ boundary_dwell_s`；`lease_max_duration_s ≥ boundary_dwell_s`；`manager_liveness_s ≤ command_deadline_s`。
- 加えて timeout 駆動の fault（R_DEADLINE_MISS / R_SAFETY_LAYER_LOST / R_TIMING_VIOLATION / R_PERMIT_EXPIRED / R_ACK_TIMEOUT / R_HEALTH_CONFIRM_TIMEOUT / R_BOUNDARY_DWELL_EXCEEDED / R_LEASE_DURATION_EXCEEDED / R_MANAGER_UNAVAILABLE）は同一 `profile_hash` の下で commissioning 時に **timeout 経路で**発火させた evidence を要求する。
- **絶対上限（秒の ceiling）は本文に書いていない**（cell / 規格依存として RT0 / Rs へ carry）。
- verifier V2 は、追加の順序 `ack_timeout_s ≤ boundary_dwell_s` と `health_confirm_timeout_s ≤ lease_max_duration_s` を「Rs 確認後に足す」とした（reviewer の主張の一部が誤りだったため、根拠が薄い）。

**求める判断**
1. 絶対上限を誰が・どこで持つか（profile 外の cell 規格 / RT0 の仕様 / 本 doc に書く）。本 doc に書くなら field 単位の ceiling の出所（規格名）を示してください。
2. 上記 2 つの追加順序を採るか。採らない場合、`ack_timeout_s` と `health_confirm_timeout_s` の上限をどこで縛るか。
3. 「相対順序 + commissioning 時の fault 発火 evidence」で CD-01 の攻撃面（timeout の巨大化）が十分に閉じるか。不十分なら足りない検査を具体的に。

## 3. OPP-13 — profile registry の所在と受理・失効の権限

**背景の事実**
- 05 §3.4 (i): permit 発行は `permit.profile_hash ∈ accepted_profiles ∧ ∉ revoked_profiles` を前提にする。
- 06 §8.1: 受理 = 全 `P_*` = 0 を満たした profile_hash を `accepted_profiles` に追加。失効 = `clearance_roles` の role による `RuntimeAuditRecord`（kind = CLEARANCE_RECORDED・payload に revoked profile_hash）。
- 未定義: registry の所在（durable store・AuthorityManager 内か外か）、**受理の権限**（two-key か operator か）、**失効の権限**（誰が REVOKED にできるか）、集合の永続化と再起動時の復元。
- 関連: profile の受理は「cell の物理事実（資源の実在・上限値の真偽・zone 幾何）」を evidence に委ねる設計で、契約層は形・単調性・束縛しか検査しない。

**求める判断**
1. 受理の権限: two-key（pS / pY 相当）か、cell operator の単独か、それ以外か。
2. 失効の権限と手続（incident / layout 変更 / tooling 変更の各 trigger で誰が）。
3. registry の所在（AuthorityManager の durable store と同一か、別 store か）と、再起動時に `accepted_profiles` / `revoked_profiles` を復元できない場合の既定（起動拒否で良いか）。
