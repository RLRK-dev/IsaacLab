## 2. 作業1 の結果（2026-09-12 完了）

選択リストは `audit/op030_stagger_static_v06.json` の `stagger_v06` キーから取れた。

```
manifest op030_stagger_static_v06.json stagger_v06: roots=104 moved=420 fixed=76
  matches v06 counts (104/420/76): True
  present in native: 420 / 420  disjoint: True
  by kind: {'cell_copy': 222, 'b_only_hardware': 194, 'bay_service': 4}
  drift: group has 125, shares 125 with the selection
  A: matched=201 missing=21 roots=85 closure=False
  C: matched=180 missing=42 roots=85 closure=False
```

マニフェストが v06 の実物であることは3点で確認済み（ジオメトリ監査のリストと一致／inventory＋drops と一致／次段ビルドが同 SHA を入力として記録）。

### `missing` と `closure=False` はエンドエフェクタの違いである

異常ではない。v06 の工程・部品確認書が、セルごとに工具構成が違うと記録している。

| ST | 左腕 | 右腕 |
|---|---|---|
| A | **フィンガを外し M4 締付工具を常設** | フィンガで支持部を把持 |
| B | フィンガで被覆を把持 | フィンガで被覆を把持 |
| C | **M6 直形締付工具を常設** | **M14 直形締付工具を常設** |

実測値がこれと厳密に一致する。

| | B に無い（missing） | 自前で持つ（closure の extra） |
|---|---|---|
| A | 左手フィンガ **21** | M4 ドライバ **27** |
| C | 両手フィンガ **42** ＝ 21×2 | M6＋M14 **54** ＝ 27×2 |

**フィンガ1手分 21 個、ドライバ1本 27 個で 4 つの数がすべて割り切れる。** 名前からの推測ではなく、工程文書と一致した事実として扱える。

### したがって選択規則を改める

葉の名前で対応付けるのではなく、**根を対応付けてそのセルで閉包を取る**。

```
1. 104 本の根をセルへ対応付ける（A・C とも 85 本が対応）
2. そのセルで descendants() を取る
3. その閉包がそのセルの装備一式
```

こうすればそのセル自身の工具が自動的に入り、B の工具は入らない。現在の `closure_brings_extra` がその工具であり、捨てずに使う。

### 残っている確認

- **A と C の集合が固定側 76 個と重ならないこと。** 現スクリプトは A・C について根と閉包しか見ていない。B については `disjoint: True` を確認済み。

## 3. 次にやること — 作業2（補修）

**スクリプトは書いた。** `scripts/build_op030_v07c_support_repair.py` を実行するだけ。

```
blender --background --python scripts/build_op030_v07c_support_repair.py
```

読むのは納品 native のみ。出力は `analysis/op030_v07c_support_repair.blend` と
`audit/op030_v07c_support_repair.json` の2つ。native は書き換えない。

複製の前に、複製元へ補修を入れる。形状データを共有する方針のため、元を直せば複製先にも伝わる。

| 対象 | 補修 |
|---|---|
| `OP030A_feeder_M4_foot_*` ×2 | 足を 33 mm 下げる（底面 0.000 → −0.033） |
| `OP030A_feeder_M4_stand_*` ×2 | 脚を 33 mm 下方へ延長（**634 → 667 mm**。上面 0.648 は動かさない） |
| `source_0693_m0120_p01` c2（A） | 下部板を 30 → 68 mm へ延長 |
| `OP030C__source_0693_m0120_p01` c2 | 下部板を 30 → 68 mm へ延長 |

手法は `build_op030_stagger_supported_static_v06.py` の `extend_lower` と足の平行移動をそのまま使う。同スクリプトは `_welded_components` で対象コンポーネントを選んでいる。

**訂正 — 脚長は 667 mm、687 mm ではない。** 687 は C の値であって A の目標ではない。C は
建造時 654 mm で、足 33 mm 下げと脚 33 mm 延長を受けて 687 mm になっている（654＋33）。A は
建造時 634 mm なので、同じ補修で 667 mm になる。C の 654 と A の 634 の差 20 mm は供給器台の
据付高さの差であり、補修で埋めるものではない。前版の「634 → 687。C の実績値と揃う」は私の誤りで、
撤回する。

**数値はスクリプト内に持たせていない。** 足の落とし量は実測した底面と床面 −0.033 の差、脚の
目標は移動後の足の上面を測った値である。表の 33 / 667 は実行後に一致することの確認値であって、
入力ではない。実行後 `audit/op030_v07c_support_repair.json` の `checks` で全4対象の誤差が
2e-6 m 未満であることを確かめる（スクリプト内で assert 済み）。

制御盤の下部板は A と C が同一メッシュを共有している可能性がある。共有していれば1回直して C を
その結果に向け、していなければ各々直す。どちらでも最後に両方を実測して検証する。

制御盤本体 `p00` / `p04` の 33 mm 浮きは 3 セル共通の未処理。是正するかは Rs 裁定（§8-2）。

## 5. 背景の要点

### 試算の根拠

作業定義の秒数と保存 bank のフレーム数から導いた。作業定義合計 250.0 秒に対し A bank 238.8 秒のため、**換算係数 0.955** を一律適用。

**すべて保存アニメーション時間の相対比較であり、実機タクトではない。** 映像用の関節上限 1.2 rad/s（実測最大 0.981）下の値。

### 効いている事実

- **A の 67% はボルト作業**。支持部のハンドリングは 9.4 秒、M4 取得 31.7 秒＋締結 39.2 秒。
- **工程順序は厳密**（支持部設置 → ケーブル設置 → 端子締結）。各 ST の担当は順序付き作業列の連続区間でなければならない。
- **案④で律速が ST2 へ移る**。ST1 60.4 秒 < ST2 63.1 秒。E4（復帰最大 63.1 秒）も ST2 で、**律速と最大リスクが重なる**。
- **鏡映変換** `M(y) = diag(−1,−1,1) ＋ Y 方向 2y`。行列式 +1 の 180° 剛体回転で FK が保たれ、自己逆変換。ST1 は −3.4、ST2 は +1.2、ST3 は +5.8。
- **複製機構 `duplicate_set()` が既存**（`op030_split_layout.py:84`）。`obj.copy()` で mesh 共有、命名は `prefix + "__" + name`、`split_source_name` を刻む。作業3で再利用できる。
- **セルごとに工具構成が違う**（§2）。複製は各セル自身の工具を運ぶ。
