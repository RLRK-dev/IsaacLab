# 07-Design Status Ledger

**Purpose (Rs directive 2026-06-05 「作って」):** make it clear, later, **what failed vs. what succeeded** among the
07-Design documents — so failed approaches are **not repeated**. This file is the **authoritative SSOT** for the
lifecycle status of each design doc. Per-doc frontmatter carries a `status_ledger:` pointer back here; when a status
changes, **update this ledger** (do not let per-doc frontmatter become a competing source of truth).

**Authority note:** `%3` (ops-supervisor) built the ledger *mechanism* and drafted the classifications from sourced
evidence. The classifications are **Rs-confirmable**; entries marked **(Rs-confirm)** involve a design-outcome judgment
that the design owner (human-Rs) should ratify. `%3` takes no design/frame position — these are evidence-based status
labels, not design decisions.

## Status vocabulary

| Symbol | Status | Meaning |
|---|---|---|
| ✅ | SUCCEEDED | Implemented and achieved its goal, with evidence. |
| ⛔ | FAILED / ABANDONED | Approach proven non-viable, or abandoned for cause. **Reason + evidence mandatory (do-not-repeat).** |
| ⚠️ | QUARANTINED / MIXED | Worked in part but fidelity/validity in doubt, or outcome varies by component. |
| 🔁 | SUPERSEDED | Replaced by a newer version (pointer to successor). |
| ⏸ | PARKED | Designed but not implemented/validated; gated. |
| 🟢 | ACTIVE | Current working design. |
| 📖 | REFERENCE | Living spec or progress log — not a pass/fail item. |
